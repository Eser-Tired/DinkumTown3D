Deployment Guide

把介绍页发布到公网

本文说明如何让 site/ 这个介绍页变成一个朋友能直接打开的公网链接。 三种方案按「要不要长期维护」来选，不是按难度选。

先看结论

如果这个页面以后还会改 → 选方案 A（GitHub Pages）。

仓库已经是 public，Pages 免费且永久。改完 site/ 只要 push，链接自动就是最新的， 不需要记得「再去发布一次」——这一点是另外两个方案最容易翻车的地方。

如果只是想现在立刻发给朋友看 → 选方案 B。

一条命令出链接，不碰 git、不用配 workflow。代价是以后每次改内容都要重新发布一次并覆盖线上。

一个前提：下载链路已经通了

页面里两个下载按钮指向的是 GitHub Release 直链，实测三个链接（EXE / APK / SHA256SUMS）都返回 200， 是公网可达的。所以部署完之后，朋友点「下载 Windows 版」能直接拿到文件， 整条链路不依赖你本机的 build/ 目录，也不需要你保持开机。

方案 A

GitHub Pages 推荐

为什么不能直接在设置页里点开

这是本方案唯一的门槛，说清楚就不迷惑了。 GitHub Pages 的「分支源」模式只认仓库根目录 / 或 /docs， 而我们的站点在 site/。所以设置页里那个下拉框根本选不到它。

有两条绕路，都不推荐：

绕路一：把站点搬进 docs/

docs/ 里已经堆了 197 个文件——截图、.import 元数据、 6 份 HTML 报告。站点混进去，目录会变得很难看，以后也难拆。

绕路二：建 gh-pages 分支

内容要在两个分支各存一份，每次改动都得手动同步。早晚会不同步， 而且排查起来很费劲。

GitHub Actions 是唯一支持任意子目录的干净做法——它把 site/ 目录打包成 一个 artifact 直接交给 Pages 服务，完全绕开分支源的限制。

部署流水线

配置好之后，每次 push 会自动跑一遍下面这条链路：

图 1 · 配置完成后的自动部署链路

第 1 步 · 新建 workflow 文件

在仓库根目录创建 .github/workflows/pages.yml（目录不存在就一起建）：

name: Deploy site to Pages

on:
  push:
    branches: [main]
    paths: ['site/**']        # 只在站点内容变动时重跑，改游戏代码不会白跑
  workflow_dispatch:                # 允许在 Actions 页面手动触发一次

permissions:
  contents: read                    # 只读代码
  pages: write                      # 写 Pages
  id-token: write                   # OIDC 令牌，deploy-pages 需要

concurrency:
  group: pages
  cancel-in-progress: true           # 连推多次时取消上一次，避免互相覆盖

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site                  # 关键：只传 site/ 子目录，不是整个仓库
      - id: deployment
        uses: actions/deploy-pages@v4

三个容易写错的地方

  • path: site 必须是子目录名。写成 . 会把整个仓库（含 197 个 docs/ 文件）全传上去。
  • permissions 三行缺一不可。deploy-pages 走 OIDC 鉴权，少了 id-token: write 会直接失败。
  • concurrency 建议留着。短时间内连推两次而不取消前一次，两个部署会打架。

不需要 .nojekyll。Artifact 部署方式不经过 Jekyll 处理， 文件原样服务。只有走「分支源」模式时才需要考虑 Jekyll 忽略下划线开头的文件。

第 2 步 · 把 Pages 源切成 GitHub Actions

这一步必须在 workflow 文件已经提交到 main 之后做，否则 GitHub 会报找不到 Pages 配置。

gh api -X POST repos/Eser-Tired/DinkumTown3D/pages \
  -f build_type=workflow

如果返回「已存在」的错误，说明 Pages 之前被创建过，改用 PUT 更新即可：

gh api -X PUT repos/Eser-Tired/DinkumTown3D/pages \
  -f build_type=workflow

确认设置生效：

gh api repos/Eser-Tired/DinkumTown3D/pages --jq '{url:.html_url, build:.build_type, status:.status}'
# 期望看到 build_type 为 "workflow"

第 3 步 · 推送并验证

  1. 提交并推送 
    git add .github/workflows/pages.yml
git commit -m "新增 GitHub Pages 部署 workflow，把 site/ 发布到公网"
git push origin main
  2. 看 Actions 有没有跑绿 
    gh run list --workflow=pages.yml --limit 3

    第一次跑大约 1 分钟。状态要看到 completed / success。

  3. 打开链接

    地址是：

    https://eser-tired.github.io/DinkumTown3D/

    第一次生效可能要等 1～2 分钟。刚推完立刻打开看到 404 是正常的，等一会儿再刷新。

  4. 确认资源真的加载了

    打开页面后按 F12 看 Console 有没有 404。重点看 10 张 .webp 截图有没有加载出来—— 文字能看但图全裂，通常说明 workflow 里 path 写错了。

日常更新怎么做

配好之后就没什么流程了：

# 改完 site/ 里的任何东西
git add -A
git commit -m "更新介绍页：xxx"
git push
# 完事。约 1 分钟后线上自动是新版

改游戏代码不会触发部署。workflow 里 paths: ['site/**'] 限定了只有站点文件变动才跑。 如果你想强制重跑一次，去 Actions 页面点 Run workflow（就是 workflow_dispatch 的作用）。

方案 B

内置「发布应用」

用平台自带的托管能力，把 site/ 目录直接发布成一个在线链接。 最快的一条路，不需要碰 git、不需要 workflow。

适合什么时候用

  • 现在就想把链接发给朋友，不想折腾配置
  • 只是临时给人看一眼，不打算长期维护这个页面

代价

  • 每次更新都要重新发布一次。改完 site/ 不会自动同步，得再说一句「同步到线上」。 这是最容易忘的一步——改了本地，线上还是旧的，自己以为已经更新了。
  • 发布是覆盖式的，新内容会直接顶掉当前线上内容。
  • 链接归平台托管，不能绑自己的域名。
方案 C

第三方静态托管（Cloudflare Pages / Netlify）

这类平台的典型用法是把 site/ 整个文件夹拖进网页，几秒后拿到一个公网链接。

优点

  • 免费额度足够个人项目
  • 自带全球 CDN，国外访问速度通常比 GitHub Pages 好
  • 自定义域名配置简单，还送 HTTPS
  • 支持绑定 Git 仓库自动构建（配了之后就接近方案 A 的体验）

代价

  • 要额外注册一个账号
  • 纯拖拽模式下和仓库脱钩，以后改内容得手动重传
  • 平台、账号、域名三者多了一层依赖

如果选这个方案，建议直接连 Git 仓库而不是拖文件夹：构建命令留空，输出目录填 site。 这样能拿到和方案 A 一样的「push 自动更新」，同时多一个 CDN。

FAQ

常见问题

朋友需要装什么才能打开吗？

不需要。就是普通网页，手机浏览器、微信内置浏览器都能开。

能直接用 GitHub 仓库页看到页面效果吗？

不能。GitHub 不渲染仓库里的 HTML 文件，点进去看到的是源码。必须真部署。

这个页面需要后端或者数据库吗？

不需要。纯静态——一个 HTML 加 10 张图，没有任何接口调用。所以三个方案都能用，不存在兼容问题。

以后加了后端还能用同一套部署吗？

方案 A 不能。GitHub Pages 只服务静态文件。如果以后页面要接表单、排行榜之类的功能， 得换成 Cloudflare Pages 的 Functions 或者独立服务器。不过以现在这个介绍页的需求，静态完全够。

链接会不会过期？

方案 A 和 C 的链接只要仓库/项目还在就一直有效。方案 B 归平台管理。

我可以三个方案同时用吗？

可以，互相不冲突。但没意义——同一份内容维护多个入口，只会让「哪个是最新的」变得难以判断。选一个就行。
